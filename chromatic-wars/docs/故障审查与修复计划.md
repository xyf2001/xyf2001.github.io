# 参考 v2.2 故障审查与重构计划

本文件记录的是对上传参考工程的源码审查。源码推导不等同于运行测试；实际执行证据见 `TEST_REPORT.md`。上传的设计文件和图片用于理解任务，不用于替代最新粘贴需求。新工程独立位于 `chromatic-wars`，没有覆盖原 ZIP 或原静态网站仓库。

## 已确定的旧版问题

| 优先级 | 源码证据（参考工程） | 问题及影响 |
| --- | --- | --- |
| P0 | scripts/gpu_battle.gd 的 `_dispatch` / `_read_render` | 每步 submit+sync，并周期性读回约2.84MB完整RGBA后ImageTexture.update，不能算显存直接显示 |
| P0 | shaders/particles.glsl / bigballs.glsl | 多个粒子非原子写大球速度，伙伴原子扣能量又被普通写回覆盖，存在丢更新竞态 |
| P0 | scripts/gpu_battle.gd / shaders/spawn.glsl | 最低8粒子及向上取整打包可把2点能量变成8点；环形槽覆盖仍存活实体 |
| P0 | clear.glsl / `_consume_fatal_events` | 致死标志逐步清零，CPU却要求连续两次且跳过最初2秒，无可靠保命握手 |
| P1 | collisions.glsl | 固定检查32个链表节点、敌粒子直接双死，漏碰撞且不保留高能包剩余能量 |
| P1 | particles.glsl | 单步终点检测会跨过细网格、护盾与核心；大包占1格即全消失 |
| P1 | paint.glsl | 只显示哈希链首；反序smoothstep的结果在GLSL规范中未定义 |
| P1 | bigballs.glsl | 固定9×9采样不能覆盖细网格扫掠；对碰未对两方一致分离与反射 |
| P1 | main.gd / draw_on | GPU初始化失败后仍固定索引空的teams，报错路径会二次越界 |
| P2 | settings.gd / gpu_battle.gd | 种子未应用、领土统计恒0；旋转机枪缺少方向安全评估 |

旧版粒子32字节 `vec4 + uvec4` 与CPU分配匹配；不能把黑屏未经验证地归因于这一布局。

## 实施顺序

1. 先建立 Godot Forward+/Vulkan 真运行路径：主 RenderingDevice、渲染线程提交、storage image + Texture2DRD，中文诊断第一条真实错误。
2. 显存统一管理领土、粒子、大球、护盾、库存和核心。通过紧凑统计读回提供UI，CPU只管理16个弹药球与少量发射命令。
3. 修复碰撞所有权、发射背压与能量运算；按数据依赖设置屏障。核心进入PENDING_RESCUE，CPU回复后GPU统一确认死亡。
4. 左侧重建实体入口、半径驱动空气墙和连续输送带；所有判定与可见几何使用同一份定义。
5. 建立可执行独立规则测试、实际窗口截图、软件Vulkan运行与压力记录；明确区分Windows硬件未测试项。

## 环境事实

当前云机器预装 Godot 4.6.3，没有 `/dev/dri` 实体GPU。为运行验证，以Debian签名包安装到工作区的Mesa Lavapipe与Xvfb提供软件Vulkan；没有把战场改成CPU GDScript实现。软件Vulkan会由驱动在CPU执行Compute，它只能验证API、着色器和规则，不能证明桌面显卡60FPS或Windows驱动兼容性。
